# Load to S3 Bucket

### S3 버킷 & 키
- s3는 디렉토리 개념이 없다. 버킷과 키만 있다. 
- 버킷과 파일 주소인 key 개념만 있다. 따라서 경로뿐 아니라 파일명까지 명시해줘야 한다. 

- 대분류, 중분류를 고려한 파일 path를 만들어두면 나중에 수천 개의 파일이 쌓였을 때 데이터 조회가 빠르고, 쉬워진다. 

- Hive-style partitioning 
- 키=값 형태로 폴더 구조를 만들어서 AWS Athena, Spark에서 자동 파티션 인식 
`s3_key = f"raw-data/code=501/date=20260728/fhrs.xml"`  

- Athena에서 파일 읽을 때, 버킷의 s3 key 값을 아래처럼 조회 가능  
`SELECT * FROM my_table 
WHERE code = '005930' AND date = '2026-07-28';`

- BUCKET_NAME을 airflow variable에 등록해서 사용함. 잠재적 (DDos, Denial of Wallet)공격 대상이될수 있음. 

### load_file() 
- 멱등성(idempotency) 고려: replace=True 설정으로 재실행 시 덮어쓰기 허용 - 동일 파일 보내면 덮어쓰기

### retry 전략 
- failed_list가 0보다 많으면 실패한 작업이 있다는 의미이므로 raise Exception 해서 task 를 실패시킴
- load_files()에서 replace=True로 무조건 덮어쓰도록 ACID - Atomic(0 or 100)한 설계를 했음
- 네트워크 실패시 AWS SDK에서 auto-retry 기본값 설정되어있음 - 기본 60초, 5회 

### 로깅 및 추적 (Observability)
- 업로드가 끝난 후 "33개 xml 파일 성공적으로 S3 업로드" / 실패: 1개 (실패 파일명: test.xml)와 같이 명확한 로그를 남김. -> 디버깅 용이해짐

### 검증 전략
1. 1번 태스크 완료 확인: /data에 로컬 파일 생성 됐는가?
2. happy path: AWS S3 콘솔에서 버킷에 파일이 누락없이 올라갔는지 확인.
3. 네트워크 에러 상황: task2 도중 네트워크 차단. retry해서 덮어쓰기하는지 확인.
   
### S3 버킷에서 파일 Object URL 링크를 바로 클릭하면 403 퍼미션 에러가 나옴
- 시스템 내부에서만 사용하는 비공개(Private) 파일로서 S3 버킷과 파일 모두 퍼블릭 엑세스 차단
- 코드는 성공인데 https:// 에서 AccessDenied는 보안 설정 잘 작동하는 것
- `Share with a presigned URL` 클릭시 내용이 정상적으로 보이면 문제가 없음   

- 단일 Task로 만들더라도, 나중에 파일 개수가 늘어나면 Dynamic Task Mapping을 통해 파일별로 Task를 동적 생성하여 병렬 처리할 수 있다는 점을 머릿속에 열어두기
