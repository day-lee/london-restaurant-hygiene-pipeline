## extract 
- xml 파일 다운로드, request session 
- retry 전략: 33개 구 실패 리스트, Raise 넣어 airflow 리트라이 트리거 

### 1. 수집 

- 실시간 데이터가 아니라 배치(Batch)처리
- 실시간 스트리밍은 Kafka 사용
- /data에 임시로 공공데이터 저장 

### 1-1. requests 방식: api 요청 vs XML 파일 다운로드 
- 데이터의 시간 범위, 수집 목적에 따라 선택
#### XML download 
- 현재 프로젝트는 주 단위 배치 작업이고, 데이터 레이크, 데이터 웨어하우스, 데이터 마트 구축이 목적이라서 XML 덤프 다운로드가 적합함
- 외부 api request limit 걱정이 없고 안정적으로 수집 가능 
- 안정성 우선
#### API request
- API 요청은 실시간성, 분, 초단위의 고주기의 짧은 시간 간격 단위일 때 
- 필요한 만큼 쪼개서 트래픽을 최적화 시킬 수 있다. pagination, filter 사용 가능

### 1-2. file download: streaming vs file staging 
#### streaming (기억)
- 스트리밍 방식은 RAM 메모리에 chunk로 올려 디스크 거치지 않고 흘려보내는 방식 
    - 장점: Airflow 워커의 로컬 디스크 용량을 쓰지 않는다. I/O건너뛰므로 속도가 빠르다.
    - 단점: 멀티스레딩, 제너레이터 등 활용하는 제어 코드가 복잡해짐 
           중간에 에러가 나면 추적이 어려움. 처음부터 다시 시작해야함 
- api 요청이었다면 쪼개서 받는 pagination에 해당

#### file staging download (노트 저장)
- 로컬 파일 다운로드는 실제 디스크 SSD 공간인 airflow 워커 /tmp에 저장하는 방법 
    - 장점: 로컬 디스크에 실물 파일이 존재하므로 안정성있음. 디버깅이 쉬움 
    - 단점: 파일 크기가 크다면 airflow 서비스가 disk full 에러가 날 수 있음 

### 메모리의 데이터를 파일로 옮겨 담는 과정이 필요하다. 
- request 라이브러리로 GET 요청을 하면 바이너리 바이트로 메모리에 머문다. 
- 휘발성 데이터를 파일 입력으로 메모리에 저장하는 과정이 필요하다.

### Session으로 HTTP GET 요청 
- HTTP GET 요청함. `requests.get()`
- `timeout=30`, 응답 대기를 30초로 설정해 무한 대기를 막음 
- retry는 airflow가 매니징해줌
- Response 객체가 응답으로 왔음 
- 식별용 유저 에이전트 선언 추가하기. 제너릭한 크롬 브라우저 내용. IP 차단 방지를 위해 '매크로 아니고 파이프 라인입니다'하고 알려주는 것.
- 세션 하나 열어놓고 33개 구 반복하며 파일 저장함. `session.get()`
- 실무에서는 airflow의 HttpHook을 사용함. 세션을 유지해서 `connection pool`을 하나 열어놓고 사용함.
- session을 열어서 connection pooling, 세션 재사용이 가능해짐. `HTTP Keep-Alive` 상태임. handshake 오버헤드가 감소함. 빨라짐.

### api 요청 에러 핸들링
- 4xx, 5xx 등 에러로 파일 다운로드가 정상적으로 안되었을 떄, 에어플로우에게 에러 객체를 raise해서 retry등 후속 조치를 할 수 있게끔 해야한다. 안그러면 다운받은 xml파일에 html 문구 등이 저장되어 다음 테스트에서 에러가 난다. 
- `raise_for_status()`는 if 문 없이 달아줘도 내부에 만약 200이 아니면 에러를 던지라는 코드가 내장되어 있음. 
- `requests.exceptions.HTTPError`는 서버와 대화는 했지만 4,5xx 상태코드가 왔을 경우
- `requests.exceptions.RequestException`은 응답을 아예 받지 못함. 인터넷 끊겼거나, 서버꺼져서 반응이 없거나. 

### 리트라이 전략  
- `반복문에서 33개 구 중 누락되는 경우를 어떻게 핸들링 할 것인가?`
- 루프에서 에러가 났을 때 바로 Raise로 airflow에 에러 신호를 주지 않고, continue로 일단 모든 루프를 돌게함. 
- 실패 기록을 리스트에 담아둠. 
- 일단 정상적인 구는 다 돌고나서, 마지막에 이 실패 리스트가 empty인지 확인한다. 
- `만약 실패한게 하나라도 있으면 강제로 raise를 던져서 task가 최종적으로는 실패하게 만든다.` 
- 다시 시도할 때 누락된 구만 다시 채워넣는 구조를 만든다. -> os.path.exists() 이용해서 파일이 이미 존재하는지 확인함 
- raise는 가장 최근에 발생한 에러를 그대로 다시 던지겠다는 뜻. 

### 중간 구조 변경
- Ingestion 단계에서 1.FHRS ➔ S3 XML 다운로드로 로우 데이터를 수집하고, 수집이 끝나면 2.S3 ➔ DB 적재를 분리해서 설계했었음
- 시니어의 리뷰를 받고 두 과정을 메모리 버퍼에 올린 상태에서 동시에 진행하기로함.  
- s3를 중간 저장소로 이용할 필요가 없음  
- 인그레스 진행 중에 데이터가 이미 임시 디렉토리에 있으니, 이 시점에 DB 적재까지 한번에 처리해라. 
- 이그레스 비용: 보통 클라우드 환경에서 데이터를 넣는 것(인그레스)은 무료이나, 이그레스는 비용을 청구함. 
- 이전 설계에서는 데이터를 넣어두고나서, 다시 asw에서 이그레스해서 빼내야 했음. 
- FinOps 관점에서 이 구조는 이그레스 비용이 너무 많이 발생함.  

- Ingress: 외부에서 시스템 내부로 데이터가 들어오는 흐름 (Inflow)
- Egress: 시스템 내부에서 외부로 데이터가 나가는 흐름 (Outflow)
