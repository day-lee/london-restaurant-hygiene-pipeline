## Star Schema

### Staging Table이 필요한 이유 
- 임시 작업 공간 
- 만약 소스가 XML, CSV, API 등으로 다양하다면 staging에서 한데 모아 형태를 맞추고 DW에 적재할 수 있다. 
- 데이터 타입 정의 
- 데이터 검증 (xml_parsing에서 날짜 형식 검증, 파일 존재여부 확인, xml 헤더 개수와 실제 파싱 개수 교차 확인)
- **Truncate & Load (밀고 새로 쓰기)**: staging은 배치가 돌때마다 지우고 다시 만든다
- `TRUNCATE`는 `DELETE`와 달리 구조만 남기고 싹 지워버림. 조건적으로 지우기 안됨. 
- upsert는 update, insert로 충돌시 새로운 데이터로 덮어씌움 
- 공간 낭비 방지: 새로 덮어써지는 95% 데이터는 거의 같은 내용이라 비교해가며 넣는 것보다 단순히 일단 다 때려넣고 다음에 분류하기가 성능상 이롭다.
- 만약 완벽한 원본 이력 로그가 DB에 필요하다면 스태이징 테이블을 비우지 않고 extracted_at(추출 시간) 컬럼과 함께 데이터를 계속 아래로 쌓는(Append-only) 방식으로 운영할 수도 있다.


### fact_table, dim_table
- fact_table은 비즈니스에서 발생한 사건과 숫자, 시간에 따라 빠르게 쌓임
- dim_table은 디멘션 테이블로 팩트 테이블에 설명, 컨텍스를 제공하는 테이블
    - 속성 데이터: 보로우 코드, 보로우 이름

### Fact Table (append-only)
- dw 테이블에는 계속 append가 일어난다. 비즈니스 사건(event)가 기록되니까. 
- 신규 오픈 식당은 새로 insert된다.
- 기존 식당의 모든 값이 똑같다면 패스, rating_score, rating_date에 변화가 있었다면 새 이력 행 추가한다. 

### stg_fhrs_ratings에 row id가 따로 없는 이유
- 임시 공간 패턴에서는 소스 시스템의 고유 ID(FHRSID)만으로도 데이터를 제어하기에 충분

### Surrogate Key(대체키)
- fact_table의 fact_key
- 이 테이블의 진정한 기본키(Primary Key) 역할
- 데이터 웨어하우스(DW) 내부 관리를 위해 시스템이 임의로 새로 만들어낸 가짜 고유 식별자, 기술적 목적으로만 존재
- 비즈니스 이벤트의 번호: 새로운 레이팅이 추가됨.

### Natural Key(NK, 자연키) 존재
- 비즈니스적 의미
- ID 같이 연산이 필요없는 경우, 'str/VARCHAR' 로 지정한다.
- integer는 앞에 0이 붙을 때 잘리는 오류가 생긴다.  

### 왜 NK(fhrs_id)가 있는데 굳이 fact_key(Surrogate Key)를 새로 만드나요?
1. 변화 이력 관리 - SCD (Slowly Changing Dimensions): 새로운 레이팅을 저장함
2. 외부 변화 대응: 만약 외부 소스 데이터 xml에서 id체계를 바꾼다면 pk를 바꿔야됨

## mixed data type 문제 
- rating score에 숫자, 문자열 두 가지 형식(AwaitingInspection, Exempt)이 들어온다. 
- fact 테이블로 변환할 때 컬럼을 두개로 분리함. 원본 레이팅 컬럼, 숫자 score만 추출한 컬럼

### Dynamic Task Mapping
- 우선은 로컬 실험용이니 task 한개에서 33개 구를 다 돌고, 나중에 Airflow로 옮길 때는 '보로우 코드 1개당 태스크 1개'가 돌도록 Dynamic Task Mapping 기능을 쓰는 것이 정석
