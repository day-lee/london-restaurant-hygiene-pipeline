## Transform: `python, SQL -> dbt` 마이그레이션
-> SQL, 파이썬으로 Upsert 로직 짜는 것의 복잡함을 느끼고 dbt core를 설치해서 materialized='incremental' 옵션으로 간단히 해결함 

- 1단계: 그 원본 데이터를 가지고 리포트용 테이블을 만드는 파이썬 가공 코드를 딱 한 개만 수동으로 짜보기 - 얼마나 귀찮고 복잡한지 몸소 느껴보는 단계
- 2단계: "파이썬으로 테이블 유무 체크하고 Upsert 로직 짜는 거 진짜 비효율적이구나!"를 깨달은 뒤, 2단계의 가공 코드를 싹 지우고 dbt Core를 설치해서 materialized='incremental' 옵션을 주어 전환

## 1 단계: transform: Python, SQL 만 이용해서 만들기. 

### 1. dim 차원 데이터 먼저 만든다.
- staging 테이블에 접근해서 차원 데이터 추출한다. (보로우 코드, 이름) 
- dim table은 한번 만들어 두면 행정구역 개편이 되지 않는 이상 거의 변경이 되지 않음.
- `SCD` slowly changing dimension 그냥 비교만 해서 차이 없으면 그대로 쓰고 업서트로 이미 있는 코드는 이름 업뎃하고 없는 지역 코드는 추가한다
- 새로운 보로우 코드 발견시 insert가 일어난다. 
- 기존 보로우가 있고 이름만 바뀐 경우, on conflict에서 충돌 감지함
- do update set 의 로직이 실행되어 기존 이름을 staging에서 새로 들어온 이름으로 덮어쓴다. 
- dw_inserted_at 시간이 갱신된다. 
데이터를 테이블에 '저장(INSERT)'할 때는 ORDER BY를 쓰지 않는 것이 관계형 데이터베이스(RDBMS)의 표준이자 원칙
-> 데이터 넣을 때 정렬하는건 의미가 없음. 관계형 DB에서 테이블은 '정렬되지 않은 데이터의 주머니' 어차피 무작위로 담김
정렬은 넣을 때가 아니라 조회할 때 사용한다. 

### 2. 팩트 테이블 만든다.
- staging과 dim 테이블을 조인해서 FK로 연결되게 만든다. 

### 3. 데이터 마트를 만든다. 
- 분석을 용이하게 하기위해 미리 계산된 데이터들 
- 운영팀은 간단한 쿼리나 BI 툴에 연결해서 바로 업무에 사용한다.
    1. 구별 2점 이하 비율
    2. 구별 2점 이하 식당 리스트 
    3. 기존에는 괜찮았으나(3점 이상), 최근에 2점 이하로 위생 등급이나 리뷰 평점이 새롭게 떨어진 식당을 찾는 로직
    이 정보가 있으면 운영팀이 즉시 경고 전화를 하거나 가맹점 점검을 나갈 수 있다.
    * 4. 배달 앱 리스팅에 올라와 있는 식당 중 최근 평점이 2점 이하로 떨어진 식당. -> 앱 리스팅에 올라온 식당 테이블이 필요함 

## 2 단계: dbt 사용
### 언제 dbt를 사용하는가?
- transform 단계 
- dbt는 이미 데이터베이스에 로드된 데이터를 변환하는 툴이다. 추출은 pandas나 DB커넥터 이용 (t3_load_stg_to_db에서 다룸)

### dbt의 장점 
- dbt를 쓰면 Boiler plate (CREATE TABLE.., INSERT INTO..)를 반복적으로 쓰지 않아도 된다. 
    DDL(definition), DML(modification) - crud
- 데이터 볼륨이 클 경우, ELT에서 transformation시 모던 클라우드 웨어하우스의 컴퓨팅 파워와 자원 리소스를 이용할 수 있어서 dbt가 사용된다.
- SELECT 문 만으로 테이블을 만들 수 있어 간결함.
- ref()로 테이블간 의존성을 관리할 수 있다. Lineage를 자동으로 관리해줌. e.g. dim 먼저 만들고 fact 테이블이 만들어져야한다. 
- 새로 들어온 데이터만 골라서 Upsert 하기' 로직을 config materialized='incremental' 한줄로 관리함 - ON CONFLICT DO UPDATE 대체
- 과정: stg (원본) -> int (중간 가공/Dim, Fact) -> mart (분석용 리포트 테이블) 형태로 dbt 안에서 단계를 나눔


- 기존 프로세스의 페인 포인트를 이해하기위해 보일러 플레이트를 작성해봤다. `dlt_t4_transform_fact_dim.py`, `dlt_t5_transform_mart.py` 파일 참고

## dbt 정리  

### materialized (구체화)
- 데이터 모델을 데이터 웨어하우스에 어떤 형태로 물리적으로 저장할지 결정하는 전략 
- Materialized: transformations from source data into warehouse(tables/ views), `dbt run`
- view: 기본값. 가상 뷰. 물리적 저장 x, 모델 빌드시마다 새로 계산  
- table: 실행 시 마다 기존 테이블 삭제하고 다시 데이터 채워 넣음 
- incremental: 마지막 빌드 후 추가, 변경 데이터만 업데이트 
- ephemeral: CTE 공통 테이블 표현식 형태로 가상 모델. 테이블/뷰 둘다 생성하지 않음. 
    * ephemeral 영어 뜻은 하루살이, 무지개, 아침 이슬, 휘발성 

### materialized='incremental'
- SCD Type 1(덮어쓰기/Upsert) 전략: update+insert
- `unique_key='local_authority_code'`: 이 키를 기준으로 덮어쓸지, 새로 추가할지 결정해라. ON CONFLICT(key)와 동일 

### incremental_strategy
``` 
{{ config(
    materialized='incremental',
    unique_key=['fhrs_id', 'updated_at'],
    incremental_strategy='append'
) }}

```
#### merge
- materialized에 incremental은 `merge`가 기본 값
- `merge`는 기존에 같은 키를 가진 데이터가 있으면 update 수정하고, 없으면 추가 insert한다
- dim 테이블은 local_authority_code가 변경되면, 값이 수정되어야 한다. 
- 기존 데이터과 새 데이터를 일일히 비교하느라 연산 비용이 크다. 

#### append
- fact 테이블은 쌓이기만 하는 로그의 성격이라 time-series 시계열 데이터를 처리할 때 기존 데이터를 업데이트 하지 않는다. 
- 기존 데이터와 비교할 필요가 없어 탐색 없이 삽입하고 끝난다. 
- `incremental_strategy='append'`로 명시해줘야 한다. 
- 진자 템플릿 코드는 컴파일 할 때 if문을 무시해서 코드 라인이 달라짐. 
- 최초 빌드 시점에서는 진자 내부 쿼리는 활성화 되지 않음.
- incremental모드일때는 CTE가 활성화되어, 콤마 위치를 if 문 앞으로 바꿔 넣음.
- report용은 view로 만들어서 Looker studio에서 바라보도록 연결.

### fact table
fact 테이블은 비즈니스 이벤트가 쌓인다. 
- 오직 rating이 변경 됐을 때만 데이터를 추가하는 구조 append
- CDC change data capture
- SCD Slowly changing dimension type 2 

-> incremental model, is_incremental() 활용해 구현 

사고 과정 
fact 테이블에서 기존에 들어가있는 식당의 가장 최신 rating을 골라옴
staging 테이블의 레이팅과 fact 레이팅 비교함 
두 테이블 간 변경 사항만 통과시켜 fact에 append(insert)

### fact_key
- fhrs_id 뒤에 현재 날짜(YYYYMMDD)를 붙여서 하나의 숫자로 만듬.  
- CAST(CONCAT(s.fhrs_id, TO_CHAR(CURRENT_TIMESTAMP, 'YYYYMMDD')) AS BIGINT) AS fact_key
